# ADR-0001：按任务维护最少文档

日期：2026-10-29。状态：已采用；用户要求精简，并确认旧22 Batch退为参考、按当前目标重新排序。

## 问题

根规则要求通读十多份长文档，产品规则、状态、未来接口和逐轮证据重复出现。旧“尚未实现”与新代码并存，用户难以阅读，Agent难以判断当前目标和事实。

## 决定

- 默认只读当前上下文和当前计划，再按任务查需求、架构及局部代码。取消固定的全套概要→数据草案→全量接口详设前置流程。
- 保留简短产品目标、当前架构、状态和下一项任务；模块README只给代码入口与本地约束，AGENTS只存开发规则。
- 重要取舍用短ADR记录原因；ADR不替代产品需求、待办、使用说明或验收证据。已有平台ADR不重复迁抄。
- HTTP接口从路由／Pydantic生成OpenAPI，复用既有导出脚本及CI一致性测试。内部类型、CLI和MCP schema分别读实际定义，不伪称OpenAPI覆盖所有协议。
- 旧22 Batch、全量接口规划和逻辑数据草案保留历史参考；不再执行其过时签名、状态或顺序。未完成产品目标保留，重复的状态流水账从现行上下文移除，Git和验收记录可追溯。

## 后果

少维护多份相同事实，也更依赖任务开始时阅读实际代码。当前任务必须写明输入、期望结果、边界和必要验收；未来关键决策仍要问用户，不能借“最小化”自行删掉产品目标。归档不表示实现或验收完成。

## 参考依据

- [Michael Nygard：Documenting Architecture Decisions](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)：短记录保留重要选择、背景和后果，替代过大的决策说明。
- [Diátaxis](https://diataxis.fr/)：按读者要完成的事区分操作说明、参考和解释；本项目只借用分类思路，不照搬目录或扩写四套文档。
- [FastAPI Features](https://fastapi.tiangolo.com/features/)：从类型和路由提供OpenAPI／JSON Schema与自动接口文档；本项目当前关闭交互文档页，只复用生成契约。

以上实践用于支持本项目取舍，不把“越短越正确”当成普遍结论。
