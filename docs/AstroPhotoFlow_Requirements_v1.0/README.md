# AstroPhotoFlow 需求与设计基线 v1.0

**文档日期：2026-10-22**  
**产品形态：ComfyUI Extension + Agent 控制层 + 天文领域服务**  
**近期交付：本地单用户、Linux／WSL 测试；开源发布**  
**状态：用于开发的需求基线，不代表软件已经实现或通过运行验收。**

## 核心结论

AstroPhotoFlow 要成为**人和 Agent 共同使用的本地天文图像处理工作台**，而不是一个聊天面板，也不是通用命令执行节点合集。

保留 ComfyUI 原生画布和执行引擎，以 Extension 集成产品；参考 `comfyui-mcp-panel` 与 `comfyui-mcp` 的实时画布桥接、受控工具调用和 AgentBackend 分层。天文软件适配、共享项目状态、素材版本、运行来源及项目记忆由 AstroPhotoFlow 自己实现。参考项目中的前端桥接与后端抽象已从源码核验。[S01](08_调研来源与核验记录.md#s01) [S02](08_调研来源与核验记录.md#s02)

**完整产品链路：**

> 创建项目、导入素材 → 安装适配包并检查外部软件 → 发现操作、展示节点 → 手动或 Agent 配置同一工作流 → 执行并检查真实结果 → 比较版本、保存来源与项目经验 → 重启后继续工作。

## 已确定的产品决策

| 决策 | 本版结论 |
|---|---|
| 开发起点 | 官方 ComfyUI 作为运行宿主；自己的 Extension 作为主产品，不全面改造 Desktop |
| Agent 路线 | 对 artokun 两个项目做受控复用与裁剪；不先将编排层整体改写成 Python |
| 外部软件路线 | 显式适配协议 + 每操作节点 + 独立执行环境；不把任意 Shell 当作默认 Agent 工具 |
| 状态权威 | 项目服务保存已确认版本；画布保留编辑草稿；运行保存不可变快照 |
| 首版范围 | 素材库、图像比较、历史版本、项目记忆全部保留 |
| 科学数据 | FITS／科学数据引用走主链路，显示预览走独立通道 |
| 第一批工具 | Siril 为首个真实适配器，ASTAP 为第二个跨软件适配器；另建受控 MCP 示例验证协议 |
| 首版环境 | WSL 内运行服务、ComfyUI 和工具；浏览器访问。独立桌面安装包不是前置条件 |
| 发布原则 | 固定依赖版本、保留上游许可、分清代码复用和设计借鉴 |

Siril 的脚本／管道接口和 ASTAP 的命令行定位接口有官方文档依据，但适配器开发与本地集成测试仍需完成。[S11](08_调研来源与核验记录.md#s11) [S12](08_调研来源与核验记录.md#s12)

## 如何使用这套基线

01 定义“必须交付什么”，02—05 约束实现方式，06 记录借鉴决策，07 定义如何验收，08 保存证据。发生冲突时，以明确的产品约束和验收条件为准，不以某个参考项目的默认行为替代需求。

`P0` 表示首版必须；`P1` 表示后续增强。阶段只是开发顺序，不等于削减 P0 功能。文中示例字段、工具名、节点名和接口均是 **AstroPhotoFlow 拟定契约**，除明确标注外，不是 ComfyUI 或参考项目已提供的 API。

## 本次调研的可信边界

依据为本次对话中用户粘贴的原始需求与公开仓库的 README、许可证、关键源码、官方接口文档。未直接访问用户 WSL 内的三份 Markdown 原文件。

本次属于静态资料与代码核验，没有安装并实际运行这些扩展，没有完成天文素材处理或兼容性测试。大型仓库只审阅与本方案相关的关键路径，不能视为全仓库审计。来源链接中的 `main`／`master` 会变化；开发启动时必须另行锁定 commit SHA，不能把本文件的日期当作依赖锁文件。

## 相比此前草案的实质修正

- 不再以 Langflow 或全面 Fork Desktop 为开发中心。
- 参考 Agent 项目的实现路径，但不假定它已经提供 AstroPhotoFlow 的权威状态、科学数据管理与完整追溯。
- 不承诺任意工作流都能在浏览器关闭后无损编辑；首版只对受支持节点提供无界面编译能力。
- 不把“首版不做额外缓存”误写成“ComfyUI 没有缓存”。外部操作节点的缓存语义必须显式处理。
- 不默认公开 GitHub 仓库都允许复制代码；ImageMagick 示例的授权情况列为阻断项。

**最终验收不是“Agent 接通”，而是“人和 Agent 能共同完成、比较、追溯并继续一条真实天文处理流程”。**
