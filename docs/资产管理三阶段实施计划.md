# AstroPhotoFlow 资产管理三阶段实施计划

**更新日期：2026-10-22；关联任务：T01。**

本计划划分 T01「数据库与图像资产管理」的三阶段建设内容。第一阶段已在 `feature/database` 实现并通过本阶段验收；第二、三阶段仍待后续指令。全量阶段均按下述范围推进，不能将阶段一完成视为整个资产模块完成。实际验证见[第一阶段交付与验收记录](第一阶段交付与验收记录.md)。

返回[开发总计划](开发计划.md)；全量资产需求及参考实现批次见[数据库与图像资产管理实施计划](数据库与图像资产管理实施计划.md)。T01 的阶段划分和交付顺序以本文件为准；第一阶段的目标、接口及停止线以[第一阶段技术与接口设计](第一阶段技术与接口设计.md)为准。

## 开发分支与合并规则

- 数据库与完整资产管理的三个阶段统一在 Git 分支 `feature/database` 上开发，包括相关领域服务、迁移、代理、前端、测试及文档变更。
- `feature/database` 是分支名称，不是源码目录；既定的 `service/`、前端及扩展入口位置不变。
- 实现 worktree 必须检出 `feature/database`，不能在 `main` 或 `dev` 上直接实施本模块。
- 第一阶段、第二阶段验收通过后，只在该分支保留阶段成果并交付记录，不合并到 `dev`。阶段完成后停止，等待下一阶段指令，不因尚未合并而继续扩展开发。
- 只有三个阶段全部开发完成，各阶段验收及必要的三阶段集成回归均通过，且没有未解决的阻断性问题后，才具备将 `feature/database` 合并到 `dev` 的条件。
- 达到合并条件后报告验收证据与合并就绪状态；本计划不授权 Agent 自动合并，实际合并按用户后续指令执行。

第一阶段可复制的执行指令见[第一阶段执行 Prompt](第一阶段执行Prompt.md)。

## 已确定的基础方向

- 前端沿用 Vue 3、TypeScript、Vite、Tailwind 4，资产状态与接口契约使用 Pinia、Zod。
- 后端采用独立 FastAPI 服务，通过 SQLAlchemy 2、Alembic 管理独立 SQLite 数据库。
- 内容散列使用 BLAKE3，Python 环境使用 uv 管理。
- 在 AstroFlow Section 侧栏面板内直接呈现共享资产库，沿用官方 Assets 的布局和交互设计，连接我们自己的资产业务与数据库；低频配置集中管理。
- 资产采用本机单用户跨项目共享库；项目引用指定资产版本，中间产物归属项目。不再要求所有资产必须属于某个项目。
- 保留已完成的侧栏入口及主题继承，不重复原有通过性验收。

## 第一阶段：整体框架与基础连通

**目标：连通侧栏内资产工作区、同源代理、领域服务及数据库；配置可管理，资产只读。**

| 部分 | 建设内容 |
|---|---|
| 资产界面 | AstroFlow Section 侧栏以五个 AstroPhotoFlow 模块按钮划分素材库、节点仓库、可安装软件、Agent 聊天和设置区域；素材库和设置区连接第一阶段实际功能，其余三个区域只显示未接入提示；校准素材在资产库内筛选，不打开独立窗口或页面 |
| 界面状态 | 提供加载、空列表、服务不可用和请求失败状态；尚未接入的操作明确不可用 |
| 后端服务 | 建立独立 FastAPI 应用、共享本机配置、本地令牌认证、健康及能力接口 |
| 数据库 | 建立 SQLAlchemy 基础层、Alembic 初始迁移；包含项目、设备、拍摄配置、项目配置关联、资产、资产版本和项目资产引用 |
| 配置接口 | 项目、设备和拍摄配置可创建、编辑、归档／恢复；项目配置关联可调整；使用 revision 防止旧版本覆盖 |
| 资产接口 | 只读查询共享库、校准素材、共享当前版本及项目固定版本引用；不提供任何资产写入接口 |
| 前后端连通 | 经 ComfyUI 同源薄代理读取真实服务；令牌只由后端持有，不使用模拟资产冒充已实现能力 |

**阶段验收：**

- 能在 AstroFlow Section 侧栏中直接展示资产工作区；内部导航不跳转，保持宿主主题及画布。
- 项目、设备、拍摄配置及关联形成真实管理闭环，服务重启后可读，旧 revision 修改被拒绝。
- 共享／项目资产查询范围正确，项目引用固定版本；产品库保持真实空库，空列表与服务错误可区分。
- 独立数据目录、新库初始化、已有库显式迁移、必要备份及恢复说明可用。
- 新增行为测试、实际 OpenAPI 和交付记录完成。

**第一阶段停止线：**上述配置管理与只读查询闭环验收完成后停止。不得继续增加文件导入／复制／扫描、BLAKE3 计算、资产引用修改、成品发布、格式解析、预览、校准匹配、科学处理、AssetTask／队列／runner、软件 Node、MCP 或 Agent。生产库不写入演示资产。未通过验收仅修复本阶段问题，通过后等待下一阶段指令。

第一阶段通过只代表阶段完成，成果继续保留在 `feature/database`，不得合并到 `dev`。第二阶段开始前等待用户指令。

第一阶段已按 S1 服务与数据库、S2 配置管理、S3 资产只读查询、S4 代理与工作区、S5 验收交付完成，具体契约见[技术与接口设计](第一阶段技术与接口设计.md)，证据见[交付与验收记录](第一阶段交付与验收记录.md)。

## 第二阶段：基础资产管理闭环

**目标：让真实文件能够导入、形成资产版本，并在界面中查询和查看。**

| 部分 | 建设内容 |
|---|---|
| 文件导入 | 支持引用／复制两种方式，记录来源、位置、大小和存储方式 |
| 内容身份 | 后台计算 BLAKE3，建立资产与内容版本的关联 |
| 后台任务 | 增加 AssetTask，展示导入、校验、解析和预览的实际状态 |
| 元数据与预览 | 先打通 FITS 的首条完整路径，科学原件与派生预览分别保存 |
| 资产界面 | 将真实资产接入卡片、列表和详情区域，展示版本、来源及任务状态 |
| 持久化 | 重启后可以继续查询资产、版本、任务及已生成预览 |

**阶段验收：**

- 同一文件可分别以引用和复制方式导入，两种模式清楚可辨。
- 资产具有明确共享／项目范围、稳定资产 ID 和版本 ID；项目使用固定版本引用。
- FITS 元数据及预览对应正确的内容版本。
- 原始文件不被修改，失败或中断不显示为成功。

**阶段出口：**完成第二阶段验收与交付记录后停止，成果继续保留在 `feature/database`，不得合并到 `dev`；收到第三阶段指令后再继续。

## 第三阶段：完整素材库与多类型扩展

**目标：将单文件闭环扩展为适合实际天文项目使用的资产管理工作台。**

| 部分 | 建设内容 |
|---|---|
| 目录与批量管理 | 文件夹索引、批量导入、目录重扫及逐文件处理结果 |
| 素材组织 | 标签、角色、筛选、分页、集合及固定成员顺序的集合版本 |
| 多类型资产 | 扩展常规图像、相机 RAW、XISF、NPY／NPZ 和已录制天文视频 |
| 类型专属查看 | 按格式接入 HDU、数组成员／切片、视频封面及逐帧查看 |
| 来源与变化 | 展示资产管理流程和实际处理来源；识别引用文件变化、缺失及新版本 |
| 恢复与性能 | 完善中断核对、预览重建、备份恢复和大文件处理基准 |

**阶段验收：**

- 目录重扫不会重复创建未变化的资产。
- 历史素材版本与集合成员不会随当前文件变化而被覆盖。
- 各格式明确展示其入库、解析和预览能力。
- 视频范围为已录制文件；NumPy 范围先覆盖 NPY／NPZ 文件。
- 具体格式、数值类型和预览方式，以第三阶段开始前确认的支持矩阵验收。

**阶段出口与合并条件：**第三阶段完成后，核对三个阶段的验收记录，并执行必要的跨阶段集成回归。仅在三阶段全部完成、测试通过且无阻断性问题时报告可以将 `feature/database` 合并到 `dev`；测试未通过则仅修复已确认的问题，不扩展新的阶段。实际合并等待用户指令。

## 三阶段共同约束

- 共享／项目范围、稳定资产与版本身份、原件保护和必要备份从首次使用时落实；共享不表示互联网公开。
- 未实现、处理中、失败和不可用分别展示，不填造处理结果。
- 三阶段只建设资产管理；软件 Node、MCP 和 Agent 继续按开发总计划推进。
- 每阶段仅验证新增或实际修改的行为；原侧栏通过性结果沿用。阶段交付后停止，收到下一阶段指令再继续。
